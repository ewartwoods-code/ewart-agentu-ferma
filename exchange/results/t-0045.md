# t-0045 — Full-auto autopilot on the Secret MacBook

## What machine this is

`/Users/secretingredient/ewart-woods-farm` on `Secrets-MacBook-Air` — NOT the
`/Users/maksimsjekimovs` machine every earlier autopilot artifact assumed. That
single fact is the root of most of what follows.

Per `exchange/secret/BRINGUP-INSTUKCIJA.txt` (pulled from origin mid-task) this
machine's farm identity is **`secret`**, so the generic 2-worker
`com.ewartwoods.farm-autopilot` agent that was installed first was removed again
and replaced by `com.ewartwoods.secret-autopilot` (one worker, `WORKER_ID=secret`).

## Defects found and fixed

Each of these silently prevented the autopilot from working. None was visible
from the supervisor side, because a broken tick still exits and still logs.

1. **Hardcoded repo path.** `scripts/autopilot.sh` and `scripts/farm-status.sh`
   both carried `REPO="/Users/maksimsjekimovs/ewart-woods-farm"`. On this account
   the job would start, find no repo, and exit 1 forever while looking installed.
   Both now derive `REPO` from the script's own location, with a `FARM_REPO`
   override. (Hermes independently made the same fix in `694e464`; the two
   collided in git — see "Merge" below.)
2. **The single-run lock defeated the whole 2-worker design.** The lock was one
   file per repo, so worker 2 always found worker 1's lock and logged
   "another autopilot run is active - tick skipped". `farm-workers.sh 2` really
   ran ONE worker. Reproduced in a sandbox harness before the change. The lock is
   now per worker (`state/autopilot.lock.<worker>`), which is what it was
   actually for: stopping one worker slot from overlapping itself when a tick
   outlives the 15-minute interval.
3. **`git pull` sat outside the mutex.** Two workers pulling the same clone at
   the same moment race on `.git/index.lock` — the exact stall that idled the
   farm 19:24-21:16Z on 2026-08-16. The pull now runs under the same lock as
   commit+push.
4. **Reservations never expired.** A worker killed mid-run (Mac sleeps, launchd
   kills the job, power loss) left `state/reservations/<num>` behind forever and
   that task was never picked again by anybody — a silent, permanent stall of one
   queue slot, on the machine least likely to stay awake. Reservations now record
   the owning pid and are reaped on a dead owner, on a missing pid past a
   1-minute grace window, or after a hard TTL (`AF_RESERVATION_STALE_MIN`, 120m).
5. **Detect-only ticks leaked their reservation.** With `AUTOPILOT_EXECUTE=0` the
   task was claimed and never released, so two dry runs in a row reported
   different tasks and hid the real head of the queue.
6. **`shlock` is macOS-only.** On Linux the call fails, which the script read as
   "someone else holds the lock", so it never ran there at all. `O_EXCL`
   (`noclobber`) fallback added.
7. **Only `index.lock` was self-healed.** A leftover `HEAD.lock` wedges every
   future commit/pull exactly the same way. The self-heal now covers
   `HEAD.lock`, per-ref locks, `objects/maintenance.lock` and stray
   `objects/*/tmp_obj_*`, all under the same 2-minute age rule.
8. **`state/.gitignore` said `state/failures/`** — i.e. `state/state/failures/`,
   matching nothing. The machine-local failure counters showed up as untracked
   and would have been swept into the shared repo by the next `git add -A`.
   Corrected to `failures/`.

## Merge with Hermes's parallel fix

Hermes's `694e464` and this work both replaced the hardcoded `REPO` line, so
`git pull` conflicted and left the clone mid-merge — with conflict markers inside
`scripts/autopilot.sh`. That state is dangerous in this codebase specifically,
because the autopilot's own `git add -A` would have staged the markers as if they
were the resolution and committed a syntactically broken autopilot.

Resolved by keeping this side's version, which is a strict superset (same
script-relative `REPO`, plus the `FARM_REPO` override); origin changed nothing
else in that file — verified as a single hunk against the merge base.
`scripts/secret-worker/bringup-secret.sh` now detects and finishes an interrupted
merge or rebase *before* any `add`/`commit`, refuses to commit a file still
containing `<<<<<<<`, and refuses to commit an `autopilot.sh` that fails
`bash -n`. Proven against a fixture left deliberately mid-merge.

## Claude CLI

`npm install -g @anthropic-ai/claude-code` failed on this Mac (stock nodejs.org
`.pkg` puts npm's global prefix in root-owned `/usr/local/lib/node_modules`;
Anthropic's docs explicitly warn against fixing that with `sudo`). Switched to the
documented native installer, which needs no root and auto-updates:
`curl -fsSL https://claude.ai/install.sh | bash` → `~/.local/bin/claude`,
version **2.1.233**. `~/.local/bin` is not on launchd's default PATH, so the
Secret plist now carries an explicit `PATH` (and `FARM_REPO`, and
`WorkingDirectory`).

  reservation staleness, reaping, pid recording and the grace window).

  routed it to provider `claude`, and committed+pushed (`8ba6d8c`) — the whole
