## What changed

**File touched:** `app/src/public/index.html` only. Nothing else in the repo,
no migration, no deploy, no spend, no keys read.

1. **`depthScale(topPct)`** (`index.html:2145-2168`) — the one function that
   turns a Y position (0-100%, the same `top%` every agent already carries
   from `scenePosition()`) into a scale factor:
   ```js
   const PERSPECTIVE_MIN_SCALE = 0.55;   // farthest character (top of the scene)
   const PERSPECTIVE_MAX_SCALE = 1.35;   // nearest character (bottom of the scene)
   function depthScale(topPct){
     const y = Math.min(100, Math.max(0, Number(topPct) || 0)) / 100;
     return PERSPECTIVE_MIN_SCALE + y * (PERSPECTIVE_MAX_SCALE - PERSPECTIVE_MIN_SCALE);
   }
   ```
   Both constants are the tunables the task asked to keep in one place.

2. **Applied on every render** (`index.html:2589-2592`, inside `renderAgents`):
   right after `pos.top` is set as the element's `top%`, the same value sets
   a CSS custom property: `el.style.setProperty('--depth-scale', depthScale(pos.top).toFixed(3))`.

3. **Applied live while dragging** (`index.html:2383-2386`, inside
   `moveAgentDrag`): the same call runs every pointer-move, using the drag's
   live `agentDrag.at.top`, so the character visibly grows/shrinks as it is
   carried up or down the field, before the drop is even saved.

4. **CSS consumers of `--depth-scale`:**
   - `.figure` (`index.html:212-224`) — `transform: scale(var(--depth-scale,1))`
     with `transform-origin: 50% 100%` (bottom-center). Anchoring the scale
     to the *bottom* of the figure means the growth happens upward from the
     feet/shadow line — the character never floats or sinks as it resizes.
   - `.agent-name` (`index.html:319-338`) — same `--depth-scale`, so the name
     tag reads as part of the same body at a distance.
   - `.bubble` is **deliberately left unscaled** (documented in the CSS
     comment at `index.html:330-334`) so speech is always fully readable, near
     or far — this is the "choose what reads best" call the brief left open.

## Design decisions / one deviation from the literal brief

- **The task's literal formula was inverted from its own stated mapping.**
  Brief text: `scale = min_scale + (1 - y_normalized) * (max_scale - min_scale)`,
  with "`y_normalized = 0` at top/far, `1` at bottom/near -> far is small, near
  is big." Plugging `y=0` into that literal formula gives `scale = max` (i.e.
  far = BIG), the opposite of the sentence describing it. Implemented the
  version that actually produces far=small/near=big
  (`scale = min + y * (max - min)`), matching the owner's stated intent
  ("jo tālāk... jo MAZĀKS... jo tuvāk... jo LIELĀKS") rather than the literal
  algebra. Documented inline at `index.html:2157-2164` so nobody re-derives
  the "bug" later. Flagging this for Hermes as a spec defect, not fixing the
  brief itself.
- **Why `--depth-scale` on `.figure`/`.agent-name`, not the outer `.agent`
  div:** the outer `.agent` element already owns `transform:translate(-50%,-50%)`
  for positioning plus its own hover/dragging transforms
  (`translate(...) scale(1.06/1.10)`). Composing a third, position-dependent
  scale into that same transform string would have required re-deriving the
  translate offset every time depth-scale changed (to keep the anchor point
  correct) — simpler and safer to give the depth scale its own transform on
  an inner element with its own `transform-origin`, which nests multiplicatively
  with the outer transforms (hover/drag still work, they just compose with
  whatever depth-scale is current) without touching the positioning logic at all.
- **Hit area:** no extra JS/CSS was needed. The `pointerdown` listener lives on
  the outer `.agent` element (`index.html:2608-2611`, unchanged), and the
  scaled elements (`.figure`, `.agent-name`) are its DOM descendants. Browsers
  hit-test a click against the actual painted (post-transform) geometry of the
  topmost element at that pixel, then bubble the event up the real DOM tree —
  not against the ancestor's own unscaled layout box. So a bigger, scaled-up
  figure is already clickable over its full visual area, and a scaled-down one
  is only clickable over its (correctly smaller) visual area, satisfying "hit
  area uses the SCALED size" with zero extra code. This is a reasoned
  conclusion from how CSS transforms and event bubbling work, not something
  this session could click-test live (see verification gap below).
- **Y-domain used:** the raw `top%` a character already carries (0-100,
  practically clamped to `POS_MIN=3`/`POS_MAX=97` by the existing drag/save
  code), the exact same number `scenePosition()` already resolves through
  every restore path (DB row -> localStorage -> `pos_x`/`pos_y` -> grid
  fallback) — so depth scaling automatically works in every scene and after
  every restore path with no new code branch.
- **Independent of pan/zoom:** `--depth-scale` is computed purely from the
  scene-relative `top%`, never from `view.zoom`/`view.tx`/`view.ty`. Panning
  and zooming only change `scene.style.transform`
  (`applyView()`, `index.html:2186-2190`); the per-agent depth scale keeps a
  character's size fixed relative to the scene at its own depth while the
  world zoom changes on top, exactly as the brief asked.
- **Applies to all agents, boss included** — the task did not ask for an
  exception, and applying it uniformly keeps the mapping simple and one
  formula.
