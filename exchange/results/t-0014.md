## What I did

### 1. The design

**The mapping, one exchange pair -> one `tasks` row**

| exchange side | app side |
|---|---|
| `exchange/tasks/NNNN-slug.md` | one `tasks` row, `title = "[t-NNNN] <title>"`, `description = objective + source path` |
| contract `kind` / `- **type:**` / `- **agent:**` | `tasks.agent_id` (which character stands in the field) |
| no result file yet | `status = 'active'` -> the minion is visible and working |
| `exchange/results/t-NNNN.md` exists | `status = 'review'`, `result_summary = "[<envelope status>] <summary>"` -> the approve button appears in the bubble |
| owner clicks the approve tick | `status = 'done'` — **the bridge never does this itself** |

Three decisions worth stating, because they are deliberate:

1. **The bridge never sets `done` or `rejected`.** A finished result becomes
   `review`, which is exactly what `PRODUCT-VISION.md` asks for ("finished work
   waits in the bubble for the owner to approve it"). Auto-approving would delete
   the owner's only decision point.
2. **`queued` is not used.** `ferma-supabase-backend.md` §4 records that no RPC
   can produce `queued`; `admin_create_task` starts a task at `active`. Rather
   than add an RPC for a status nothing reads, an unfinished exchange task maps
   to `active` — which is honest: it is open work assigned to that agent.
3. **No new table, no new column, no new RPC, no service-role key.** The external
   key is the `[t-NNNN]` prefix inside `title`, which the bridge reads back from
   the public-read `tasks` table with the anon key. `admin_create_task` and
   `admin_mark_task_review` already insert the `agent_events` row themselves
   (migration `20260815231727...sql:105-106` and `:133-134`), so the event history
   the task asked for comes for free.

**Agent routing.** `app/supabase/seed-agents.sql` seeds 7 minion characters +
Herme; `AGENTS.md` defines 9 working roles. Two characters therefore carry two
roles each — stated in the code (`scripts/sync-tasks-to-db.js:52-63`), not hidden:

| character | role(s) it stands for | example kinds |
|---|---|---|
| `milk` (Slauc govi — the data collector) | Research Agent | `research`, `data collection` |
| `eggs` (Lasa olas — collects results) | Ads Analyst **+** Reporter / Reviewer | `analysis`, `report`, `verification` |
| `chop` (Cert malku — cuts) | Ads Optimizer | `ad`, `bid`, `budget`, `campaign` |
| `plant` (Stada kartupelus — grows) | Content Agent **+** Visual Agent | `content`, `copy`, `image`, `video` |
| `mow` (Plauj zali — trims) | SEO Agent | `seo`, `keyword`, `tags` |
| `pigs` (Gana cukas — herds stock) | E-commerce / Ops Agent | `shopify`, `inventory`, `price`, `order` |
| `dig` (Rok bedri — digs foundations) | Coder (KODERIS) + infrastructure | `code_local`, `setup`, `autopilot`, `migration` |
| `herme` | fallback only — anything unclassifiable | — |

Priority: an explicit `- **agent:** Ads Analyst` line beats every keyword guess;
then the ordered kind rules; then Herme. Both task-file shapes in the repo are
handled — the contract-JSON shape (t-0001, t-0013..t-0015) and the bullet shape
(t-0002..t-0012).

### 2. What was built

- **`scripts/sync-tasks-to-db.js`** (573 lines, new). No dependencies, node >= 18.
  - `--dry-run` is the **default** and touches no network at all: it prints the
    mapped rows and the RPC calls it *would* make, as JSON on stdout.
  - `--apply --yes` is the only write path — **two** flags, plus `SUPABASE_URL`,
    `SUPABASE_ANON_KEY` and `FARM_ADMIN_TOKEN` read from `process.env` only.
    Nothing is hardcoded; the token goes into the RPC body and is never printed,
    not even in the error path (`sync-tasks-to-db.js:389-397`).
  - Idempotent: a second run over unchanged data issues zero RPC calls. Rows
    already `done` or `rejected` are never reopened; rows without the `[t-NNNN]`
    prefix (anything typed by hand in `/control`) are never touched.
  - `--task t-NNNN` limits the run to one task, so a go-live can be staged.
- **`scripts/test-sync-tasks-to-db.js`** (292 lines, new). 27 offline checks
  against the real `exchange/` files plus two temp-dir fixtures, with
  `globalThis.fetch` replaced by a counter that throws.
- **`app/README.md`** — "What is missing" #4 and "Suggested next steps" #1
  rewritten: the bridge now exists but has only ever run in dry-run, and turning
  it on needs the owner. (The old text said no such code existed.)

**What I did NOT verify, and why**

- **No live database call of any kind.** This task is `code_local`: I never held
  `SUPABASE_URL`, the anon key or the admin token, so the RPC round-trip, the
  `tasks` read-back and the resulting `agent_events` rows are **unverified
  against the live database**. They are verified only against the SQL in
  `app/supabase/migrations/20260815231727_agent_farm_tasks_skills_chat_usage.sql`
  and the RPC contract in `ferma-supabase-backend.md`.
- **`execute` on `admin_create_task` / `admin_mark_task_review` for `anon`.**
  Migration 3 adds no explicit `grant execute`, so the bridge relies on
  Postgres's default `PUBLIC` execute grant — the same path `/control` already
  uses successfully from the browser with the anon key (`app/README.md` "What
  works right now"). I could not read `information_schema.role_routine_grants`
  to confirm it. **First real run must check this before anything else.**
- **No policy read-back was run** (`ferma-supabase-backend.md` §6): I changed no
  SQL, so no policy changed — but I did not re-read the list to prove it.
- **Nothing was deployed.** `scripts/` is not part of the app build, and this
  repo does not deploy anything anyway: the live site builds from
  `ewartwoods-code/ewart-agentu-ferma` `main`.

## Go-live plan

**What the owner must approve (all of it is outward-facing or paid):**

1. **The first real write.** `--apply --yes` inserts ~15 rows into the live
   `tasks` table and flips three characters (`dig`, `eggs`, `milk`) to working on
   the public site. Visitors see it immediately. Cost: EUR 0 — it uses the anon
   key + the existing admin token, no paid API.
2. **Handing the admin token to a script.** `FARM_ADMIN_TOKEN` would have to live
   somewhere the runner can read it (a local file with `chmod 600`, or a launchd
   `EnvironmentVariables` entry). It must not enter git, the autopilot log, or a
   result file. Rotating it stays a one-line `update` on `app_secrets`.
3. **The historic backlog.** 13 of the 15 tasks are already finished, so a full
   first run puts 13 items into the approval queue at once. Two options — owner's
   call: (a) approve them in bulk with a one-off script call to
   `admin_approve_task` so the field shows only live work, or (b) leave them in
   `review` and let him clear the bubbles himself. I recommend (a) for the ones
   Hermes has already accepted, then let the bridge run forward-only.

**How it would then run (no further approval needed once 1-3 are settled):**

- Same launchd slot as the autopilot: `scripts/autopilot.sh` already runs every
  15 minutes and is the natural place for one extra line —
  `node scripts/sync-tasks-to-db.js --apply --yes` after the push step, so the
  farm scene updates within a minute of Hermes dropping a task or Claude writing
  a result. Adding that line is a one-line change to `autopilot.sh` and should be
  a separate task, after the first manual run proves the RPC path.
- Rerunning is safe by construction: unchanged rows produce zero RPC calls.

**Security guard — what stays true:**

- No new table, column, RPC or policy. The RLS invariant is untouched: still one
  `select` policy per table, still no `insert`/`update`/`delete` for `anon`,
  still no policy on `app_secrets`.
- Every write goes through the existing token-gated `admin_*` RPCs. The bridge
  needs **no service-role key** — the anon key plus the admin token is enough,
  which keeps the strongest key out of the loop entirely.
- The bridge runs on the Mac, not in the browser and not on Railway, so the admin
  token never reaches a page template.
- Approve/reject stay human. The bridge cannot mark anything `done`.

**Deploying to `ewart-agentu-ferma` / Railway: not needed.** The bridge is a
local script that talks to Supabase directly. Nothing in `app/src` changed, so
there is nothing to push to the deploy repo and no Railway rebuild. The only
change visible on the live site is the data the bridge writes.
