# t-0036 — Annual goal 1M EUR: monthly plan, weekly loop, goal panel, price program

**Scope honesty first.** This was `code_local`. Every change is in this repo. Nothing was
deployed, no live price / listing / ad / budget was touched, the migration was written but
**not applied** to any database, and no paid key was enabled or read. The app change is
**not live** — `app/src/` here is a snapshot; the live site deploys from
`ewartwoods-code/ewart-agentu-ferma`.

## What I did

### 1. The plan is computed, not typed — `scripts/annual-goal-plan.js`

The owner will move these inputs. A typed table goes stale the first time he does, so the
plan is a script and the JSON, the plan document and the app config all come out of it.

- Year target 1,000,000 EUR over **2026-09 .. 2027-08**, split by a Q4-weighted seasonal
  curve times a 1.0x -> 3.0x growth ramp, then renormalised.
- **The twelve months sum to exactly 1,000,000** — largest-remainder allocation, so no
  month is rounded on its own and the year still adds up. Same for the channel split
  within each month.
- Units per channel = target / average order value, and the Amazon per-market allocation
  puts 70% behind the markets that measurably sell and 30% into an explicit expansion
  budget (otherwise the plan targets 0 EUR in Italy forever).

Output: `data/annual-goal-plan.json` + `knowledge/owner-strategy/annual-goal-monthly-plan.md`.

### 2. The evidence base — and how thin it is

| What | Figure | Source |
|---|---|---|
| Shopify, 30d | 5,730.14 **USD**, 46 orders | `data/shopify-overview.json` |
| Amazon EUR zone, 30d, **ad-attributed only** | 3,787.34 EUR, 65 orders | `exchange/results/t-0003.md` §1 row 1.1 |
| Etsy | nothing | no connector (`data/README.md`) |

Annualised that is ~68.8k USD (Shopify) plus **at least** 45.4k EUR (Amazon ad-attributed)
plus an unmeasured Etsy — roughly a **9x gap** on what we can currently see. The true gap
is smaller by however much organic Amazon and Etsy turnover exists, and **nobody in this
workspace knows that number.** That is week-1 task G1, and it is why the app shows no
progress bar.

Everything used to shape the target carries `measured: true|false` and its source. The
Etsy AOV (65.00 EUR), the FX rate (0.92), the channel split, the seasonal curve and the
ramp are all marked as assumptions and render with `(est)`.

### 3. The "Merki" band — first block on the main screen

`app/src/public/index.html`: CSS at :438, markup at :1290, config at :4587, renderers at
:4758–4968, wired into the poll at :5032 and the first paint at :5087.

Four blocks, in the owner's order: **year goal + progress**, **12-month plan table with
channel split**, **this week's task list + Friday result**, **Monday price proposals**.

Same two-source arrangement as the personas band: it paints from the computed config
before any database answer (so it works with Supabase down), and the `goal_*` / `price_*`
rows win once the migration is applied. The source line always says which of the two is on
screen, and distinguishes "table missing" from "table empty".

**The three honesty rules built into it, each with a test:**

1. **No progress bar without a measured actual.** With nothing measured the bar is drawn
   as a striped "no data" strip and the line under it explains why. It does not show
   "0.0%", which would read as a measurement of zero sales.
2. **An actual figure without a source is refused.** The database enforces it with a check
   constraint; the page checks it again, because that number is what the bar is drawn from.
3. **An agent's suggestion never renders as owner-approved.** `agreed` is its own chip in
   its own colour, separate from status. All six seeded tasks show "vel nav saskanots".

The seeded task list (G1..G6) is built from finished work — t-0003's 45.7% DE ACoS,
its 361.52 EUR of zero-sale spend, Italy's 25,950 impressions with zero orders, t-0035's
ready-but-unfed Etsy method — because the owner asked for next tasks to come out of
results. Each task shows which result suggested it.

### 4. The price-increase program — `scripts/price-proposal-generator.js`

Proposals only; the script cannot change a price.

- Margin ladder (under 35% -> +12%, 35-45% -> +8%, 45-55% -> +5%, at target -> +3% only
  with 10+ units proven), capped at +15% per step, no proposal under 3 units/30d, and
  `cost >= price` escalates as loss-making rather than being re-priced.
- Each proposal carries the number that actually matters for the max-profit hunt: the
  **break-even volume retention**, `(old_price - cost) / (new_price - cost)`. For the
  worked case (40.00 -> 44.80, cost 30.00) that is 67.57% — a volume drop of up to 32.43%
  still leaves profit level. That figure is on every line in the app.
- `--track` compares before/after **per day** (a 30-day before and a 9-day after are
  otherwise not comparable) and returns `more profit` / `less profit` / `flat` /
  `too early` (under 7 days) / `no data`, each with what to do next.

**The blocker, stated rather than papered over:** `data/product-master.csv` has no price,
no cost and no units, and nothing else in the repo does either. Any "current price" would
be invented. So with no price file the generator prints the catalogue shortlist (ranked by
how many platforms carry each product — a multi-platform product is the safer place to
test a raise) plus the exact export needed. The arithmetic is proven against fixtures, so
it is ready the day the export exists.
