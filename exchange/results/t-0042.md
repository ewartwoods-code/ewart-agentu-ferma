## What I did

Owner's ask (t-0042): every agent must show which strategy it works by, and the strategy list
itself must be registered/viewable/improvable inside the farm app (not just in `knowledge/`
files nobody in the app ever sees).

### 1. No-fabrication data pipeline (`scripts/build-strategy-data.js`)
Reads `knowledge/strategy-map.md` + all 11 files in `knowledge/owner-strategy/*.md` and writes
`app/src/public/strategy-data.js` — a `window.STRATEGY_DATA` snapshot the app loads client-side,
exactly the same pattern the app already uses for `PERSONAS` (migration 20260817180000) and
`ANNUAL_GOAL` (migration 20260817200000): a generated config paints before the first database
answer and survives Supabase being down; a real DB row wins over it, field by field, once one
exists. Title, status and body are extracted from each file's own text (the `## Status` section,
not guessed from the filename); nothing is invented. Re-run after editing any strategy file:
`node scripts/build-strategy-data.js`.

Also updated `knowledge/strategy-map.md` itself (deliverable 3, "Sync"): added the two files it
was missing (`influencer-strategy.md`, `annual-goal-monthly-plan.md`) and — the important part —
added an explicit honesty note: the map's "Agent" column names *conceptual* specialist roles
(Ads Optimizer, SEO Agent, ...) from `AGENTS.md`/`knowledge/agents-inventory.md`, but the app's
real `agents` table holds a disjoint set of ids (the visual minion characters). Only `herme`
(tier=`boss`, established as the Supervisor elsewhere in `CLAUDE.md`/`farm-operator.md`) has a
legitimate, non-fabricated match. `scripts/build-strategy-data.js`'s `AGENT_LINKS` constant
encodes exactly that one link and nothing else — see the comment block at its top.

### 2. Migration (created, NOT applied) — `app/supabase/migrations/20260817223000_strategies_registry.sql`
Three tables, same RLS invariant as every other table in this app (public read, no public write):
- `strategies` — the DB-editable home for the registry, same relationship to
  `strategy-data.js` that `personas` has to the `PERSONAS` config.
- `strategy_agent_links` — which real `agents.id` works by which `strategies.slug`. Left
  **empty** by the migration on purpose (seeding a guess here would be exactly the fabrication
  the owner's rules forbid).
- `strategy_edits` — the "Uzlabot" proposal queue. `status` starts `'pending'`.

Two RPCs, same conventions as every other RPC in this schema:
- `submit_strategy_edit(p_strategy_slug, p_proposed_by, p_proposed_text, p_note)` — open
  (`grant execute ... to anon`), same shape as `submit_command()`. Validates non-empty text,
  a real strategy slug, and a length cap.
- `admin_review_strategy_edit(p_token, p_edit_id, p_approve, p_review_note)` — token-gated,
  identical check to every `admin_*` RPC. Approving only **records the decision** in the table;
  it does not and cannot rewrite the actual `.md` file from inside Postgres — turning an approved
  edit into a real file change stays a separate, explicit code task, per the "no silent edits"
  requirement in the task's definition of done.

Not applied to the live database (code_local — no live data writes), exactly like migrations
20260816190000/20260817160000/20260817180000/20260817200000 before it.

### 3. App wiring — `app/src/public/index.html`
- New `<script src="strategy-data.js"></script>` loads the snapshot before the main script.
- Profile modal (`Profils` tab): new "Stratēģija" section (`#mStrategy`, right after Skilli).
  `openModal()` calls `strategyLinksForAgent(a.id)` and either lists clickable strategy chips or
  says plainly that no strategy is linked yet.
- New Herme-menu entry "📚 Stratēģijas" opens a registry overlay (`#strategyOverlay`) listing
  every strategy — title, status pill (draft/active/review), which conceptual role uses it,
  clickable.
- New detail overlay (`#strategyDetailOverlay`): full text (`<pre class="strategy-body">`,
  scrollable), an "Ierosināt uzlabojumu" toggle revealing a form (proposed text, name/agent,
  note), and a list of any strategy_edits still pending for that slug.
- `loadAndRender()`'s main poll now fetches `strategies` and `strategy_agent_links` via the
  existing tolerant `sbGetOptional()`, and `applyStrategies()` / `applyStrategyAgentLinks()`
  merge DB rows over the config exactly like `applyPersonas()` does.
- The submit handler calls `sbRpc('submit_strategy_edit', ...)` and, if the RPC doesn't exist yet
  (404 / PGRST202 — i.e. the migration above isn't applied), shows a clear Latvian message
  instead of a raw error, same convention `control.html`'s `sbRpc()` already uses.
