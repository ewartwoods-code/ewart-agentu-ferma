### Part A — the token meter

**The honest core of it.** There is no API this app can call that reports how
many tokens are left on a Claude Max / Pro subscription — the Anthropic Admin
usage API covers a Console **API organization**, which is a different billing
surface from the subscription the Mac autopilot spends. So the meter is built on
two clearly separated quantities:

- **used** = a *measured* number from `agent_usage`, and
- **left** = *(a budget the owner typed)* − used, labelled as exactly that.

It never presents a fetched balance, and it never draws a bar from a number that
does not exist.

**`/api/usage/sync` was finished, not papered over** (`app/src/server.js:186-340`):

- The hardcoded `cost_usd: 0` is **gone**. The sync path writes token counts
  only; cost stays untracked, and the UI says "izmaksas netiek uzskaititas"
  instead of rendering a confident `$0.00` (`ferma-code-quality.md` §2 item 2 —
  outstanding item closed, "finish it or remove the field": the field was removed
  from the sync path).
- The double-count bug was fixed. `input_tokens` and `uncached_input_tokens` name
  the *same* quantity in different revisions of the report, so at most one is
  counted (`INPUT_FIELDS_EXCLUSIVE`, `app/src/server.js:222`); the two cache
  fields are genuinely separate spend and are added on top
  (`INPUT_FIELDS_ADDITIVE`, `:223`). `sumTokenFields()` (`:299-308`) implements
  that rule.
- **Self-verifying first run** (`app/src/server.js:336-338`): this code has never
  run against a real Admin key, so the response echoes `fields_seen` — the
  numeric keys the API actually returned. If the field names differ from the ones
  summed, the first real run says so instead of silently producing a wrong total.
  Treat the numbers as unverified until that check has been made; the honesty
  contract in the file header (`:191-213`) states this in the code itself.
- Every written row records `source: USAGE_SOURCE` (`:263`), so a number can be
  labelled by provenance rather than implied to have been measured.
- A missing-migration guard (`hasUsageSourceColumn()`, `:288-296`, called at
  `:240`) returns one clear 503 instead of an opaque per-agent PostgREST error.

**The meter UI** (`app/src/public/index.html`):

`meterHtml()` (`:1160-1204`) has **three states and no fourth**:

| what is known | what is shown |
|---|---|
| used + budget | bar, `used / budget`, `Atlicis N (x%)`, colour green→amber→red at 70/90% |
| used only | the measured number + "atlikums nezinams — budget not set" |
| neither | "Tokeni vel nav sinhronizeti" — **no bar at all** |

The trap this deliberately avoids: `agent_usage.input_tokens` defaults to `0` in
Postgres, so a never-synced row still carries numbers. `usedTokensFor()`
(`:1140-1144`) therefore keys on `last_synced_at` and returns **null**, not zero,
for an unsynced row — a zero is never rendered as a measurement.
`sumUsage()` (`:1147-1155`) totals only synced rows and reports `synced / of`,
so the owner sees the coverage of the number, not just the number.

The meter appears in four places: the always-visible platform band on the field
(`:1246`), the platform panel (`:1301`), each minion's own profile
(`:1497` — showing that minion's **share** of its platform's budget, because the
remainder belongs to the platform not to one minion), and Herme's farm-wide panel
(`:1664-1674`), which draws **one bar per platform** rather than one total — a
Claude budget and a GPT budget are not one pool and must never be added together.

The control panel gained the budget editor (`app/src/public/control.html:238-269`
markup, `loadBudgets()` `:513-533`, save handler `:610-642`), which explains in
Latvian why the owner has to type the number himself.

### Part B — the hierarchy

`buildHierarchy()` (`app/src/public/index.html:1115-1127`) turns the flat `agents`
roster into: **platforms at the top → specialists nested by `parent_id`**, plus an
explicit `orphans` list. Design points:

- **A new AI platform is data, not code.** Adding GPT / Gemini = one `agents` row
  with `tier = 'platform'` + `parent_id` on its specialists. There is no hardcoded
  platform list anywhere in the page.
- **Unassigned specialists are surfaced, not hidden** — they render as a
  "Bez platformas" card (`:1257-1266`) pointing at the control panel.
- **Herme is never nested** under a platform (only `tier = 'minion'` rows nest).
- **The pre-migration state is labelled, not faked.** Until migration
  20260816190000 is applied there are no `platform` rows, so the page falls back
  to a single Claude group tagged **"priekskatijums"** (`PLATFORM_PREVIEW`,
  `:1092-1098`; the tag at `:1244` and `:1289`). It is a view, not a data source —
  every number under it is still summed from the real specialist rows.
- Nothing breaks pre-migration: `sbGetOptional()` (`:1106-1114`) degrades only the
  feature that needs a missing table, never the page.

Surfaces: the always-visible band on the field (`:682-685` markup,
`renderPlatformBand()` `:1223-1272`), the platform panel with its clickable
specialist list (`:761-789` markup, `openPlatformPanel()` `:1277-1341`), the
grouped roster in Herme's panel (`:820-823`), and the control-panel editors
(`app/src/public/control.html:204-236`, handlers `:569-607`).

**Migration** `app/supabase/migrations/20260816190000_agent_hierarchy_and_token_budgets.sql`
(198 lines, additive + idempotent): widens `agents_tier_check` to allow
`platform`, adds `agents.parent_id` (self-FK + index), adds `agent_usage.source`,
creates `token_budgets` (RLS on, **select-only** policy), and adds three RPCs —
`admin_upsert_platform_agent`, `admin_set_agent_parent`, `admin_set_token_budget`
— each `security definer set search_path = public` and each opening with the
standard `value = p_token` guard. `admin_set_agent_parent` also refuses a
self-parent and refuses a parent that is not a platform.
