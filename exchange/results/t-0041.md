## What I did

### 1. The shipping-cost engine — `scripts/shipping-cost-engine.js` (651 lines)

The task asked for a spec. A spec that nobody can run is a spec that drifts, so the
rule set is executable code with the spec written into it.

**Chargeable weight.** `chargeableWeight()` (line 149) returns
`max(actual, L*W*H / the courier's own divisor)`. The divisor is per courier and comes
from that courier's contract — the same box bills at 48 kg on a divisor of 4000 and
38.4 kg on 5000, and that difference alone flips which courier is cheapest (proven in
the test suite, and visible in the `--example` run below).

**The one rule.** A price may only come out of a rate card. There is no default
divisor, no assumed fuel surcharge, no extrapolation above the top weight break.
Each field is one of three things and they are treated differently:

| in the file | meaning | what the engine does |
|---|---|---|
| a number | read from the contract | uses it |
| `0` | a measured zero (a contract genuinely without a fuel surcharge) | uses it as a real zero |
| `null` | unknown | **BLOCKED**, naming the exact field. Never silently 0 |

**Four decisions**, so a human reading the log knows who has to act:

| decision | meaning | who acts |
|---|---|---|
| `CHOSEN` | quoted from real data, cheapest eligible courier wins | nobody — it proceeds |
| `BLOCKED` | data is missing; `missing` lists exactly what | the owner (send the data) |
| `NO_ELIGIBLE_COURIER` | data exists, but nothing may carry this parcel | a human packs it differently |
| `EXAMPLE_ONLY` | quotes came from the example card | hard stop — must never happen live |

**The order of the rules matters and is enforced:** the country rule is applied
*before* any quote, so a contractual lock cannot be undercut by a cheaper courier,
and the decision record says in plain words that price was not allowed to decide.
Ranking is cheapest → fewest transit days → the country's preferred courier →
courier id, so the same shipment always produces byte-identical output.

**Blocked vs ineligible are kept apart** on purpose: "DPD has no GB zone on this
contract" is knowledge (ineligible, nobody needs to do anything), while "we do not
know DPD's fuel surcharge" is a data gap (blocked, the owner must act). Merging the
two would bury the owner's to-do list inside noise.

### 2. The data files

- **`data/shipping-rate-cards.json`** — the four couriers the owner named (FedEx, UPS,
  DPD, Latvijas Pasts). Every price, divisor, limit and surcharge is `null`, and the
  file carries its own hard rule saying no number may be written into it from memory
  or from a public tariff page. Origin country LV is sourced from
  `data/shopify-overview.json` (`store.country = "Latvia"`); the dispatch postcode is
  an open question.
- **`data/courier-country-matrix.json`** — 13 destination countries, each with the file
  it came from: the ten Amazon marketplaces with listings plus SA/AE (connected venues,
  zero listings) from `data/amazon-venues.json`, plus LV from the Shopify snapshot.
  Not one country was added because it seemed likely — a test re-derives the list from
  `amazon-venues.json` and fails if a country appears with no channel behind it. Every
  `required_courier` / `preferred_courier` is null and every row is `UNCONFIRMED`.
- **`data/shipping-rate-cards.example.json`** — invented numbers, existing only to show
  the owner the shape of the file and to give the tests something to check arithmetic
  against. It sets `is_example: true`, and the engine will never return `CHOSEN` from
  it; the best it can produce is `EXAMPLE_ONLY`. A test flips the flag to prove the
  lock is that flag and nothing else.

### 3. The browser flow — `knowledge/order-approval-agent-flow.md` (238 lines)

Nine steps (S1 detect → S2 read order → S3 build the shipment → S4 compare couriers →
S5 confirm → S6 buy label → S7 print → S8 mark processed → S9 daily reconciliation),
each with what it produces and what makes it stop. Two rules run through all of them:
never act on a page without first asserting the order id on screen matches the order in
memory, and never mark an order processed before a label actually exists.

**S9 exists because of a failure nobody would otherwise see:** comparing what the label
actually cost against what the engine quoted is the only way a stale rate card gets
noticed before the courier's invoice arrives.

The per-channel feasibility table answers the owner's "best done in a browser"
directly: **true for Etsy and seller-fulfilled Amazon** (no working connector —
`AGENT-FARM-ROADMAP.md:15` records the Etsy API failing on shared-secret/403, line 16
records Seller Labs as NOT CONNECTED), but **not true for Shopify**, where a read API
demonstrably works from this Mac (`data/shopify-overview.json` was captured through it
on 2026-08-16). Browser where there is no API, not everywhere.

**Money gates.** Quoting and deciding are free and auto. Buying a label spends money, so
it needs a per-parcel ceiling *and* a daily cap, and Phase 1 is dry-run: the agent
decides and logs, confirms and buys nothing, until a week of its decisions has been
compared against what Signie actually did.

## Notes for Hermes

**The task assumed the missing input was prices. It is not the only one — and probably
not the worst one.** Courier prices are a copying job: the owner has the contracts and
filling `data/shipping-rate-cards.json` needs no code change. But the engine also needs
a **packed weight and box size for every product**, and the repo holds exactly one
sourced product size and zero weights. Chargeable weight is `max(actual, volumetric)`,
so without a box size a light 3 kg parcel could legitimately bill at 48 kg — which is
why the engine refuses to quote from a weight alone rather than quoting low. Measuring
206 products is real work; a **packing rule** ("box = product + 4 cm each side, weight
x 1.25") would unblock everything far faster and is the decision worth putting to the
owner first.

**Scope reality on Amazon.** FBA orders are picked, packed and shipped by Amazon and
never reach this agent. Until someone states which of the ten live marketplaces still
produce seller-fulfilled orders, the size of the Amazon half of this job is unknown —
it could be most of the work or none of it.

**PII is a real decision, not a formality.** Every previous task in this workspace
deliberately avoided order-level data because orders carry names, addresses and emails
(`data/README.md`). This agent cannot work without reading exactly that. Where order
data may live needs an answer before S2 runs even once, and the answer must not be this
git repository.

**Naming.** The task says "Order & Shipping / Apache" and lists couriers as "DPD
(Diegels)" and, in one place, "Backend Pasts". Read as DPD and Latvijas Pasts;
registered as "Order & Shipping". Both readings are recorded in the data files so
nobody has to guess again — but confirm, especially "Diegels".

**On turning it on.** The engine is ready for the day the data arrives, but the browser
half is not proven and browser automation on marketplace UIs is fragile by nature. The
Phase 1 dry-run in section 4 of the flow doc is not ceremony: a week of the agent's
decisions compared against Signie's own choices is the cheapest way to find out whether
the rate cards are right before the first real label is bought.
